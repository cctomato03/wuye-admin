# 小区物业管理系统 · 系统设计

## 1. 背景与目标

为物业服务企业提供多租户 SaaS 化的物业管理系统，一套部署服务多家物业公司、多个小区，
在 **数据隔离、权限边界、万级小区规模** 三个前提下覆盖物业日常业务闭环。

设计目标：

1. **公司级隔离**：物业公司即租户，公司之间数据完全不可见；
2. **小区级授权**：同一公司内，员工只看到被授权小区；
3. **业务闭环**：小区基础信息 → 住户/人员 → 车辆车位 → 收费账单 → 设备门禁；
4. **可运维**：单可执行文件交付、迁移可重跑、关键路径有审计与监控；
5. **可扩展**：层级自定义、房屋业态多样（住宅/别墅/商业楼/商铺/办公），字段按业务可演进。

## 2. 角色与权限模型

### 2.1 角色
| 角色 | 范围 | 说明 |
| --- | --- | --- |
| 平台超级管理员 | 平台默认租户 + 全部数据 | 管理物业公司、小区、平台级配置与监控 |
| 物业公司管理员 | 本公司 | 新建公司时自动创建，拥有除平台配置外的全部菜单 |
| 公司内自定义角色 | 本公司 | 由公司管理员创建，菜单与可管理小区不得超出创建者 |

### 2.2 权限模型

> **租户边界**：组织与权限（用户/角色/部门/岗位/员工）按物业公司隔离；
> 平台默认租户可在组织页切换任意物业公司（tenantId 参数 + OrgTenant 校验），
> 物业公司用户只能管理本公司，跨公司请求返回 403。
>
> **默认角色**：首次部署仅 super_admin（全权限）与 pm_company_admin（物业管理员：
> 除系统设置/系统监控/菜单管理外全部权限）；新建公司自动克隆「物业管理员」。

```
用户 ──< 用户角色 >── 角色 ──< 角色菜单 >── 菜单(目录/页面/按钮)
                       └──< 角色小区 >── 小区          （community_scope=2 时生效）
用户 ──< 直接授权小区 >── 小区
```
- 菜单三种类型：目录（分组，path 为子页面前缀）、页面（路由）、按钮（permission 权限码）。
- 接口鉴权：`middleware.Perm("模块:资源:动作")`。
- 数据权限：
  - 租户：`tenant_id` 过滤（平台超管例外）；
  - 小区：可见集合 = 角色可管理小区 ∪ 直接授权；`community_scope=1` 表示本公司全部（含后续新增）。
- 越权防护：
  - 角色创建/授权：小区 ⊆ 调用者可管理小区，菜单 ⊆ 调用者已有菜单；
  - 用户创建/分配角色：角色必须属于本租户；
  - 写操作前 `MustCommunity` 校验目标小区在范围内。

## 3. 数据模型

### 3.1 租户与小区
- `pm_company`：物业公司档案（编码、名称、信用代码、联系人、状态），与 `tenant_id` 一一对应。
- `pm_community`：小区（归属唯一物业公司），含五级行政区划编码（省/市/区县/街道/社区）、地址、负责人、客服电话、规模统计。

### 3.2 小区基础信息（层级 + 房屋）

**层级 `pm_structure_node`**（小区为根的一棵树）
- `parent_id=0` 表示直接挂在小区下；`level_no`、`path`（如 `0,101,102`）由服务维护，改上级会级联更新子树。
- `node_type`：1 区域 / 2 楼栋 / 3 单元 / 4 楼层（取自字典 `space_node_type`）。
- `category`：住宅楼/别墅/商业楼/办公楼/车库/配套/其他（业态标识）。
- 规模：地上/地下层数、单元数、电梯数、建筑面积、建成年份、结构、交付日期、位置描述。
- `full_address`：**自动生成** = 上级地址 + 本层名称（顶级 = 小区地址 + 名称），改名/换上级时递归刷新。
- 同级名称唯一（服务校验 + `uk(community_id,parent_id,name,deleted)` 语义索引）。

**房屋 `pm_house`**
- `node_id` 指向所属层级；`0` 表示直接挂在小区（不限层级）。
- 面积：建筑面积（必填）、套内、公摊；层高、户型、朝向、装修。
- 属性：用途（住宅/商业/办公/车位/其他）、房屋类型（户型模板）、状态（空置/自住/出租/装修中/停用）、
  产权性质、是否临街 + 门面宽（商铺）、是否可售、附属设施、交付日期。
- `building_id/unit_id/floor_id` 为路径上的冗余引用（便于按楼栋统计与兼容查询）。

**多业态建模**
| 业态 | 层级路径示例 | 说明 |
| --- | --- | --- |
| 普通住宅 | `1栋/1单元/1层/101` | 逐级建立，房屋挂楼层 |
| 别墅 | `别墅区/1号别墅` | 一栋一套，房屋直接挂楼栋节点 |
| 商业楼/商铺 | `商业楼/1层/101铺` | 房屋用途=商业，可标临街与门面宽 |
| 办公楼 | `办公楼/5层/501` | 用途=办公 |
| 车位 | 车辆管理中维护车位档案 | 不占用层级类型 |

### 3.3 人员与住户
- `pm_resident`：住户档案（证件、联系方式、紧急联系人，跨小区唯一）；
- `pm_resident_house`：住户-房屋关系（身份：业主/家属/租户，有效期、主联系人、状态），历史变更记录 `pm_resident_house_log`；
- `pm_visitor`：访客登记（受访房屋按 `house_id` 关联，有效期与进出状态）；
- `pm_other_person`：其他人员（保姆/装修工等，按分类与有效期）。

### 3.4 资产

> 单位、车辆、住户、访客等所有「挂房屋」的业务，统一通过级联选房组件选择「层级 → 房屋」并保存 `house_id`，避免手工输入房号造成关联歧义。
- `pm_merchant`：单位商铺（`house_id` 必填）；
- `pm_vehicle` / `pm_parking_space`：车辆与车位（`house_id` 关联，车位可售/可租、标准费用）。

### 3.5 收费
```
pm_fee_item(项目) ──< pm_fee_standard(标准：生效区间×单价)
        │
        └──< pm_bill(账单：房号/业主/账期/用量/金额/状态)
pm_meter(表计) ──< pm_meter_reading(抄表) ──> 生成用量账单
pm_account(房屋余额) ──< pm_account_flow(充值/扣款流水)
```
- 计费方式：按面积·月、按面积·天、按用量、固定金额、按套。
- 账单状态：未缴 / 部分缴 / 已缴 / 已作废；支付方式：现金/微信/支付宝/余额。

### 3.6 设备与门禁
- `pm_device`：门禁机/道闸/摄像头等，`bind_node_id` 绑定任意层级（兼容旧的 `bind_level/bind_id`），`access_enabled` 表示参与门禁。
- 授权下发：给定「房屋 + 人员」，按 `房屋 → 层级路径各级 → 小区` 收集启用门禁设备，生成授权与卡片记录；
- 撤权：删除人员-设备授权并记录日志；门禁开关、重试、撤销均可在页面操作。

### 3.7 系统与权限表
`sys_user/role/menu/dept/post/dict_type/dict_data/config/file/job/log_login/log_oper/notice/message/todo`、`schema_migrations`。

## 4. 关键流程

### 4.1 新建物业公司（开户）
```
平台管理员提交 → 创建租户 + 公司档案 → 建根部门 → 建内置角色「物业公司管理员」
→ 角色授予除(系统监控/系统设置/物业公司与小区/菜单管理)外全部菜单 → 建管理员账号 → 返回一次性密码
```
公司管理员登录后可在本公司内创建角色/用户/部门/岗位/员工，并维护小区业务数据；无权创建公司/小区。

### 4.2 小区基础信息建设
1. 平台/公司建小区（行政区划五级 + 地址 + 负责人）；
2. 建层级（上级 + 名称 + 类型），地址自动串接；
3. 房屋挂层级或直接挂小区（编码 + 建筑面积必填）；
4. 大批量场景：下载模板 → 填「房屋编码 / 房屋地址 / 房屋面积」→ 导入：
   地址以「小区地址+小区名称」开头，按 区/栋/单元/层(楼)/号 切分层级，缺失层级自动补齐后挂载房屋；
   导入为"全量校验 + 单事务写入"：任一行不合格整批不导入并逐行回执错误；
5. 需要时导出全量房屋明细；导入出错可「清空层级与房屋」整体重置（有住户/账单/车辆/单位/访客数据时拒绝，设备自动解绑）。

### 4.3 住户入住与门禁
```
住户登记（证件回显） → 绑定房屋（身份/有效期） → 上传人脸 → 门禁授权下发 → 可查卡片/撤销
```

### 4.4 收费闭环
```
建收费项目 → 配标准 → 生成账单（按账期/按抄表） → 缴费（现金/在线/余额） → 生成流水 → 对账与统计
```

## 5. 非功能设计

### 5.1 性能
- 分页查询上限 200；列表都必须带 `community_id` 与 `deleted` 条件以命中索引。
- 禁止循环查库：集合场景先收集 ID，再一次 `IN` 批量查询（在线用户/菜单/房屋/住户）。
- 慢 SQL 阈值 200ms 打日志；工作台统计性能有回归断言（< 2s）。

### 5.2 安全
- JWT 双令牌（access 2h / refresh 7d），支持旧密钥过渡与吊销黑名单；
- 登录失败锁定（5 次 / 10 分钟）、验证码 + 滑块可开关；
- 密码强度最小长度校验；上传白名单扩展名与大小限制；
- 所有写操作记录操作日志（含字段级 diff）。

### 5.3 可运维
- 迁移版本化 + 启动期幂等结构校验（`EnsureSchema`）；
- 健康检查 `/healthz`、Prometheus `/metrics`、Swagger `/swagger/index.html`；
- 定时任务（清理过期令牌、在线集合）可配置开关。

### 5.4 审计与删除
- 全表 `create_by/create_time/update_by/update_time`；
- 逻辑删除（`deleted` 毫秒时间戳），唯一索引包含 `deleted` 以支持编码复用；
- 关键业务（住户房屋关系、门禁下发、账单）保留变更/操作日志。
