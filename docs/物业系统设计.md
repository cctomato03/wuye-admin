# 小区物业管理系统 · 总体设计

> 目标读者：本项目的开发者与运维。
> 本文说明「数据模型、租户/小区隔离、索引与大表策略、模块与接口规划、导入模板、第三方对接预留」。
> 代码组织与开发约定沿用 [开发手册](./开发手册.md)，使用说明见 [操作手册](./操作手册.md)。

## 1. 业务定位与规模假设

| 维度 | 设计取值 | 说明 |
| --- | --- | --- |
| 物业公司（租户） | 数百 ~ 数千 | 每个物业公司 = 一个 `sys_tenant` |
| 小区 | 1 万+ | 一个物业公司可管理多个小区，一个小区只归属一个物业公司 |
| 单小区房屋 | 200 ~ 20 000 | 住宅 + 商业楼栋 |
| 单小区住户关系 | 1 000 ~ 60 000 行 | 含历史（软删除保留） |
| 全国房屋总量 | 1 000 万级 | 决定分页/统计/账单生成的写法 |
| 月度账单 | 单小区 1 万 ~ 3 万行/月 | 一年即 30 万行/小区，必须靠索引 + 批量写入 |
| 门禁授权明细 | 单小区 2 万 ~ 10 万行 | 按人 × 类型 × 设备展开 |

结论：**所有业务表必须能以 `(tenant_id, community_id, ...)` 命中索引**，禁止全表扫描型查询；
大表（账单、授权明细、进出记录）按"时间 + 小区"做归档与可选分区。

## 2. 租户、物业公司与小区的三层模型

```
sys_tenant（物业公司租户）
   └── pm_community（小区，唯一归属一个租户）
          ├── pm_region（区域/期）
          │     └── pm_building（楼栋：住宅/商业/配套）
          │            └── pm_unit（单元）
          │                  └── pm_floor（楼层）
          │                        └── pm_house（房屋：住宅/商业/办公）
          ├── pm_device（设备，可绑定到 小区/区域/楼栋/单元/楼层 任一层级）
          └── 业务数据：住户关系、访客、其他人员、车辆、单位、账单、授权…
```

三条不可越界的约束（代码与数据库双重保证）：

1. **租户约束**：任何查询都带 `tenant_id = 当前登录租户`（平台超管 `tenant_id=0` 例外，可跨租户）。
2. **小区约束**：业务表的 `community_id` 必须属于当前用户被授权的小区集合（`pm_user_community`）。
3. **层级约束**：楼栋/单元/楼层/房屋的上级 ID 必须与同一 `community_id` 一致（写入时校验，不合规直接拒绝）。

### 2.1 用户与小区授权

| 角色 | 可见小区 | 实现 |
| --- | --- | --- |
| 平台管理员（`is_super=1`） | 全部租户全部小区 | 鉴权时 `CommunityAll=true` |
| 物业公司管理员（角色 `pm_company_admin`） | 本租户全部小区 | 登录装载主体时按角色判定 `CommunityAll=true` |
| 项目经理 / 客服 / 收费员 / 门禁管理员 | 被授权的小区 | `pm_user_community` 逐条授权 |
| 未授权任何小区 | 空 | 查询被强制加 `1=0` |

> `pm_user_community` 是**唯一**的小区授权入口；新增物业员工时必须同时写授权，
> 否则他能登录但看不到任何数据（这也是防越权的默认安全姿态）。

### 2.2 隔离实现在代码中的落点

| 层次 | 机制 | 位置 |
| --- | --- | --- |
| 登录主体 | 主体缓存里带上 `CommunityIDs / CommunityAll` | `service/auth.go` `loadPrincipal` |
| 查询 | `scope.Tenant(...)` + `scope.Community(ids, col)` | `internal/model/scope/scope.go` |
| 写操作 | `Service.mustCommunity(p, id)` 校验小区归属 | `internal/service/property_scope.go` |
| 详情/改删 | 先按 `(id, tenant_id, community_id IN …)` 查，查不到即 404（不暴露存在性） | 各 service |

**约定：任何按 ID 的读写，都必须走"带作用域的查询"，不允许 `First(&x, id)` 裸查。**

## 3. 表清单

公共字段（所有业务表都有，缺一不可）：

```sql
create_by   BIGINT UNSIGNED NOT NULL DEFAULT 0,
create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_by   BIGINT UNSIGNED NOT NULL DEFAULT 0,
update_time DATETIME NULL ON UPDATE CURRENT_TIMESTAMP,
deleted     BIGINT NOT NULL DEFAULT 0,   -- 0=有效；非 0=删除时间戳（毫秒）
remark      VARCHAR(500) NOT NULL DEFAULT ''
```

- **不做物理删除**：删除一律 `UPDATE … SET deleted = 毫秒时间戳`；
- `deleted` 与唯一键组合成 `UNIQUE KEY (… , deleted)`，删掉后可以重建同名/同编码数据；
- 到期/失效用 `status` + 有效期字段表达，不写 `deleted`（历史要能查询、能续期、能还原）。

## 4. 大数据量设计要点

1. **索引左前缀**：业务表主查询索引一律以 `community_id` 打头（跨小区统计才用 `tenant_id`），
   与"用户只能看被授权小区"的过滤条件天然对齐，避免回表扫描。
2. **唯一键带 `deleted`**：`(community_id, code, deleted)`，软删除后可以重建编码。
3. **不做 `SELECT *` 的大列表**：列表查询只取展示列；详情单独接口。
4. **分页上限**：`PageQuery.Normalize()` 已把 `pageSize` 限制到 200；导出另设 `maxExportRows`。
5. **计数不失控**：列表 total 用「同条件 `Count`」，但必须先让条件命中索引；
   对 `pm_vehicle_access_log`、`pm_access_grant` 这类百万级表，列表默认**强制时间范围**（近 30 天）。
6. **批量写入**：账单生成、Excel 导入、门禁授权展开一律 `CreateInBatches(…, 500)`，
   单事务分片提交，避免长事务与 lock wait。
7. **账单按月切片**：`bill_month CHAR(6)`（YYYYMM）+ `period_start/period_end`，
   月结、欠费统计、删月重算都是"单分区式"操作。
8. **冗余计数**：`pm_house.owner_count / resident_count`、`pm_community.building_count` 等由服务层维护，
   列表页不再实时聚合（聚合查询是慢查询的主要来源）。
9. **归档策略**：`pm_vehicle_access_log`、`pm_access_grant`（已解除）、`pm_oper_log`
   可配置定时任务按 `create_time` 归档到历史表或删除；接口见 `service/job.go` 内置处理器。
10. **可选分区**：单表超 2000 万行时，对 `pm_bill`、`pm_vehicle_access_log` 按 `bill_month` / 年份做
    RANGE 分区（MySQL 8 支持，主键需含分区键）。当前设计已满足"未来可加分区"条件（不自增主键、分区键在唯一键内）。
11. **字符集**：`utf8mb4_general_ci`（与脚手架一致），车牌/证件号等查询列单独建前缀索引。

### 5.1 门禁授权规则（业务核心）

```
住户/访客：house_id → floor → unit → building → region → community
           收集每一层级 bind_level/bind_id 命中的设备（去重）
物业人员： community_id 下所有门禁设备
其他人员： 登记时手工勾选的设备
```

- 每个 `(人员, 下发类型, 设备)` 生成一条 `pm_access_grant`；
- 提交后进入 `待下发`，由 `IssueGrants` 批量调用第三方平台（当前为占位实现，见 §7）；
- 失败可**单条重试/批量重试**，成功记录时间与返回；
- 人员登记的有效期到期后，定时任务把对应 grant 置为 `过期解除` 并触发解除调用；
- 人员删除/关系解除时同步撤销。

### 5.2 收费规则

| 计费方式 | 生成逻辑 |
| --- | --- |
| 按面积·月 | `房屋建筑面积 × 单价`，按 `bill_month` 生成 |
| 按面积·天 | `面积 × 单价 ÷ 当月天数 × 实际天数` |
| 按用量 | 抄表：`(本期读数 − 上期读数) × 倍率 × 单价` |
| 固定金额 / 按套 | 按房屋数或车位数定额 |

- 住宅/商业分开计价：`pm_fee_item.house_usage` + `pm_fee_standard`（可按房屋类型覆写单价）；
- 单位（商铺/办公）走 `pm_merchant` + 同一套账单表（`merchant_id` 非空）；
- 支付方式：扫码盒子、小程序、现金、公众号、二维码、余额划扣、其他电子支付、押金抵扣、银行转账
  （`pay_method 1..9`），**当前只记账不做清分**，第三方对接见 §7。

## 7. 第三方对接预留

门禁下发/解除（`implements service/property_access_issuer.go`）：

```go
type AccessIssuer interface {
    Issue(ctx, req IssueRequest) (resp IssueResponse, err error)
    Revoke(ctx, req RevokeRequest) error
}
```

- 默认实现 `stubIssuer`：**不调用任何外部系统**，仅返回"待对接"文案并保持 `待下发 → 失败（可重试）`
  或者按配置 `property.access.stub_success=true` 视为成功，方便演示与联调；
- 对接真实平台时：实现该接口并在 `bootstrap` 里注入，无需改动业务代码。

### 10.-1 第 6 轮调整

- **层级自定义**：`pm_structure_node` 取代固定四级，房屋 `node_id`、设备 `bind_node_id`；

- **房屋一律按 ID 关联**：单位(`pm_merchant.house_id`)、车辆(`pm_vehicle.house_id`)、访客(`pm_visitor.visit_house_id`)、

- **模块合并**：员工/岗位并入「组织与权限」，不再有独立「物业公司」分组；公司与小区仍在「系统设置 → 物业公司与小区」。
- **行政区划级联**：级联值改用 `id`，节点携带 `code/level/name`，选择后回填"省/市/区县/街道/社区"与 6/9/12 位编码；
  接口 `/districts/path` 同步返回 `id` 便于回显。

### 10.0 组织与权限模型（第 5 轮补充）

```
平台超级管理员（平台默认租户）
   └── 组织与权限：用户 / 角色 / 部门 / 岗位 / 物业公司与小区（公司=租户、小区归属公司）
         └── 新建物业公司 → 自动生成管理员账号 + 「物业公司管理员」角色（本公司全部小区）
               └── 公司管理员在公司内创建：角色（可绑定小区）/ 用户 / 部门 / 岗位
                     └── 子角色：菜单 ⊆ 自己的菜单；小区 ⊆ 自己的可管理小区
```

- 任何角色、用户、部门、岗位都带 `tenant_id`，写操作按调用者租户落库，跨租户角色/小区一律拒绝；
- 小区级数据：`role.community_scope`（1 全公司 / 2 指定）+ `sys_role_community` + `pm_user_community` 三层合并；
- 平台级菜单（系统监控 / 系统设置 / 租户与小区 / 菜单管理）不下放给物业公司，避免越级改平台配置。
